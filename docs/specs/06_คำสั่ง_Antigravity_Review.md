# 06 — คำสั่งสำหรับ Antigravity: ตรวจสอบ / ปรับปรุง / ทดสอบ / Refactor

**วิธีใช้:** หลัง Freebuff ส่งมอบแต่ละ Phase → เปิด Antigravity ที่ repo `inthara-erp-v2` → วาง "คำสั่งที่ 1 (Review)" → ดูรายงาน → ถ้ามีปัญหา ใช้ "คำสั่งที่ 2–4" ตามลำดับ → ผ่าน gate ทั้งหมดจึงไป Phase ถัดไป

## คำสั่งที่ 1 — Review หลังจบแต่ละ Phase (สำคัญที่สุด)

```
คุณเป็น Senior Code Reviewer ของโปรเจกต์ Inthara Smart Water ERP v2
ภารกิจ: ตรวจรับงาน Phase <N> (ที่เพิ่งสร้างโดย AI อื่น) ก่อนอนุมัติให้ไป Phase ถัดไป

อ่านก่อน: 00_README_ภาพรวม.md, 02_สถาปัตยกรรมระบบ.md, 01_SRS (โมดูลของ Phase นี้),
03_DB_Schema_SQLite.md, 04_API_Spec.md (endpoint ของ Phase นี้), 05_แผนงาน (Phase <N>)

ตรวจ 6 ด้าน แล้วออกรายงานตามรูปแบบด้านล่าง:
1. ตรงข้อกำหนด: ทุก FR ของ SRS โมดูลนี้ทำครบไหม ระบุเลข FR ที่ขาด/ทำเกิน
2. สถาปัตยกรรม: ผ่าน Router→Service→Repo? มี SQL ใน route ไหม มี business logic ใน repo ไหม
3. ความถูกต้องข้อมูล: ทุก write ที่แตะหลายตาราง อยู่ใน transaction ไหม (ระบุไฟล์:บรรทัดที่ไม่อยู่)
   เงินเป็น satang integer ทั้งกันไหม มี floating point ปนไหม
4. ความปลอดภัย: prepared statement ทุก query? Zod ทุก input? เช็คสิทธิ์ฝั่ง server ทุก route?
   มี secret/รหัสผ่าน/ข้อมูลจริงหลุดเข้าโค้ดหรือ git ไหม (ตรวจ git log --stat ด้วย)
5. การทดสอบ: test ครบตามที่ 04_API_Spec หัวข้อท้าย + 05 ระบุไหม npm test ผ่านจริงไหม
   coverage ของฟังก์ชันคำนวณโมดูลนี้ ≥ 80% ไหม
6. คุณภาพโค้ด: ชื่อสื่อความหมาย? ฟังก์ชันยาวเกิน 50 บรรทัดไหม? โค้ดคัดลอกซ้ำระหว่างโมดูลไหม

รูปแบบรายงาน:
## ผลตรวจ Phase <N>
- ผ่าน/ไม่ผ่าน gate: [ผ่าน | ไม่ผ่าน]
- Critical (ต้องแก้ก่อนไปต่อ): รายการ พร้อม ไฟล์:บรรทัด + วิธีแก้ที่แนะนำ
- Major (ควรแก่ใน Phase นี้): ...
- Minor (ยกไปรวมที่ Phase เก็บงาม): ...
- ข้อ FR ที่ยังไม่ครบ: ...
ห้ามแก้โค้ดเองในรอบนี้ — ให้รายงานอย่างเดียว
```

**Gate ผ่าน = ไม่มี Critical และไม่มี FR ขาด**

## คำสั่งที่ 2 — ทดสอบเพิ่ม (ถ้า review ชี้ว่า test ไม่พอ)

```
เพิ่มการทดสอบให้ครบตามที่ review ระบุ โดยเขียน test อย่างเดียว (ห้ามแก้โค้ดธุรกิจ):
- ทุกกรณี Critical/Major ที่เป็น bug ให้เขียน test ที่ fail ก่อน (red) แล้วรายงาน
- ทดสอบ concurrency ตาม NFR-2 (10 check-in พร้อมกัน) ถ้ายังไม่มี
- fuzz input ตัวที่เสี่ยง (qty ติดลบ, ทศนิยม, string แทนตัวเลข, unicode) ผ่าน Zod ต้อง 400 ทั้งหมด
ส่งมอบ: ไฟล์ test ที่เพิ่ม + ผลรัน (อะไรแดงบ้าง) — ห้ามทำ test เขียวโดยการลด scope
```

## คำสั่งที่ 3 — แก้บั๊ก + ปรับปรุง

```
แก้ตามรายงาน review Phase <N>:
1. แก้ทุก Critical ก่อน รอบละข้อ รัน npm test หลังแต่ละข้อ
2. แก้ Major ทีละรายการ, commit แยกข้อ (fix: <คำอธิบาย>)
3. ทุกการแก้ต้องทำ test ที่ fail อยู่ (จากคำสั่งที่ 2) ให้เขียว — ถ้าไม่เขียวถือว่ายังไม่แก้เสร็จ
4. ห้าม refactor ผสมกับการแก้บั๊กใน commit เดียวกัน
ส่งมอบ: ตาราง ข้อ → ไฟล์ที่แก้ → ผล test ก่อน/หลัง
```

## คำสั่งที่ 4 — Refactor (หลัง Phase 4, 7, 10 หรือเมื่อ review ชี้ debt)

```
ทำ refactor (ไม่เปลี่ยนพฤติกรรม — ก่อน/หลังต้องผ่าน test ชุดเดิมทั้งหมด):
1. รวมโค้ดซ้ำระหว่างโมดูลเป็น shared (repo helpers ตาราง, ฟอร์ม/ตาราง frontend ที่คัดลอกกัน)
2. แตกฟังก์ชันยาว > 50 บรรทัดออกเป็นชิ้นที่มีชื่อชัด
3. จัดโฟลเดอร์/ไฟล์ให้ตรงโครงสร้างใน 02 (หา drift)
4. ตรวจ query ต่อ request: รัน dev log ดูจำนวน SQL ต่อ endpoint หลัก 10 ตัว — เกิน 5 ประโยคให้รวม query
5. ลบไฟล์ตาย/โค้ดที่ comment ทิ้ง/comment ภาษาไทยอธิบายจุดที่ควรเป็นชื่อตัวแปรดีๆ
ส่งมอบ: สรุปสิ่งที่ย้าย/รวม + ยืนยัน npm test ผ่าน 100% เหมือนเดิม + ตัวเลข query ก่อน/หลัง
```

## คำสั่งพิเศษ — Performance ตรวจกลางทาง (หลัง Phase 5 และ 10)

```
วัด performance ตาม budget ใน 02 หัวข้อ 7:
- ใช้ autocannon ยิง 5 endpoint หลัก (GET /api/orders, /api/customers, /api/reports/dashboard,
  POST /api/auth/login, POST /api/checkins ด้วย seed) ที่ 50 req/s นาน 30 วินาที
- รายงาน p50/p95/p99 ต่อ endpoint + จำนวน SQL ต่อ request
- ถ้าเกิน budget: วิเคราะห์สาเหตุ (index ขาด? N+1? ข้อมูลเยอะเกิน query?) แล้วเสนอแผนแก้ก่อน — ห้าม optimize แบบเดา
seed ข้อมูลทดสอบ: 5,000 ลูกค้า + 20,000 ออเดอร์ (สคริปต์ seed ที่ Phase 0 เตรียมไว้)
```

## คำสั่งพิเศษ — Security Audit (หลัง Phase 9 ก่อนขึ้นจริง)

```
ตรวจความปลอดภัยทั้งเชิงโค้ดและเชิง repo:
- ตรวจว่า data/, backups/, .env ไม่เคยถูก commit (git log ทุก path)
- ทดลอง: SQL injection ที่ทุก query param, ส่ง token scope portal ไป /api/* (ต้อง 403),
  เรียก /api/users ด้วย token staff (ต้อง 403), แก้ payload สถานะออเดอร์ข้าม server (ต้องโดน reject),
  ทดลอง XSS ในชื่อลูกค้า/หมายเหตุ (แสดงผลต้องไม่รัน script)
- ตรวจ dependency: npm audit + รายงาน CVE
- ตรวบว่า log ไม่มี password/token/PIN
ส่งมอบ: รายงานพร้อมตาราง ทดลองอะไร → ผลคาดหวัง → ผลจริง → ผ่าน/ไม่ผ่าน
```
